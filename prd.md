# PRD: Клиентский брифинг — карточка/чек-лист по клиенту перед выездом на встречу

**Версия:** 0.1 (черновик для учебного проекта)
**Дата:** 16.09.2026
**Автор:** Dayana

---

## 1. Проблема

Перед первой встречей с клиентом менеджер тратит 30-40 минут на ручной сбор разрозненной информации: гуглит компанию, ищет учредителей в реестре, пытается понять, кто будет присутствовать на встрече и о чём с ним можно поговорить помимо дела. Информация разбросана по разным источникам, часть данных не находится вовсе, а часть найденного забывается или теряется до момента встречи.

## 2. Цель продукта

Дать менеджеру за 1-2 минуты структурированную карточку-справку по клиенту, которую можно прочитать за 30-60 секунд перед выездом на встречу, чтобы:

- прийти подготовленным и не выглядеть незнакомым с базовыми фактами о компании;
- понимать, с кем именно предстоит разговаривать и кто принимает решения;
- иметь 1-2 темы для small talk помимо основной повестки;
- заранее видеть возможные стоп-факторы (просроченные налоги, споры).

## 3. Задача, которую решает результат

Автоматизировать сбор публично доступной информации о компании и лице, принимающем решения (ЛПР), и превратить разрозненные фрагменты в единый читаемый документ — вместо того, чтобы менеджер вручную открывал 5-6 вкладок перед каждой встречей.

## 4. Целевая аудитория

Основной пользователь — менеджер по продажам / аккаунт-менеджер / консультант / банковский менеджер, который регулярно выезжает на встречи с новыми или малознакомыми клиентами. Инструмент для внутреннего использования, не показывается клиенту.

## 5. Пользовательский сценарий (happy path)

1. Менеджер узнаёт о предстоящей встрече и вводит в приложение название компании и/или БИН/ИНН.
2. Система выполняет серию запросов к источникам данных (реестр, поиск, соцсети).
3. LLM обрабатывает найденные фрагменты и раскладывает их по блокам карточки, честно помечая отсутствующие данные.
4. Менеджер открывает готовую карточку за несколько минут до встречи и пробегает её глазами.
5. (Опционально) Менеджер отмечает пункты чек-листа как выполненные перед выездом.

## 6. Функциональные требования

### 6.1 Ввод данных
- Поле ввода названия компании (обязательное).
- Поле ввода БИН/ИНН (опциональное, повышает точность поиска по реестру).
- Поле ввода ФИО ЛПР, если уже известно (опциональное).

### 6.2 Сбор данных
Система должна собирать информацию по пяти блокам:

| № | Блок | Обязательные поля | Источник |
|---|------|--------------------|----------|
| 1 | Компания | название, сфера деятельности, **дата образования компании**, статус регистрации | реестр (egov.kz / kgd.gov.kz для РК, ЕГРЮЛ / nalog.ru для РФ), сайт компании |
| 2 | Налоговый статус | **налоги оплаченные / статус задолженности**, налоговый режим | kgd.gov.kz (РК), «Прозрачный бизнес» nalog.ru (РФ) |
| 3 | Лицо, принимающее решения (ЛПР) | ФИО, должность, срок в компании, зона ответственности | LinkedIn, раздел «Команда» на сайте, пресс-релизы о назначениях |
| 4 | Контекст обслуживания | текущий банк / подрядчики / партнёры (если найдено) | тендеры/госзакупки, пресс-релизы о партнёрствах, кейсы подрядчиков |
| 5 | Интересы ЛПР | хобби, публичные выступления, темы для разговора | интервью в деловых СМИ, публичные соцсети, конференции |

### 6.3 Обработка
- LLM формирует итоговый текст по каждому блоку строго на основе найденных фрагментов.
- Если по полю ничего не найдено — система явно пишет «не найдено», не домысливает и не генерирует правдоподобные, но непроверенные факты.
- Каждое утверждение в карточке должно быть прослеживаемо до источника (ссылка или пометка источника).

### 6.4 Вывод
- Итоговая карточка на один экран: пять блоков сверху вниз, с визуальным разделением.
- Чек-лист из 5-6 пунктов «готовности к встрече» под карточкой (см. раздел 8).
- Возможность отметить пункты чек-листа галочками перед выездом.

### 6.5 Дополнительно (не MVP, возможное развитие)
- История последних просмотренных карточек по клиентам.
- Кнопка «обновить» для повторного сбора данных перед повторной встречей.
- Экспорт карточки в PDF для печати.

## 7. Нефункциональные требования

- **Честность важнее полноты.** Лучше явно показать «не найдено», чем сгенерировать недостоверный факт.
- **Скорость.** Карточка должна собираться за 1-2 минуты, читаться — за 30-60 секунд.
- **Приватность.** Интересы и данные ЛПР — персональные данные; используются только сведения, которые человек сделал публичными; данные не хранятся дольше, чем требуется для подготовки к встрече.
- **Работа на мобильном.** Менеджер часто открывает карточку с телефона по дороге на встречу — верстка должна корректно работать на маленьком экране.

## 8. Стиль и UX

Деловой, справочный стиль без визуального шума — карточка должна читаться как страница из досье, а не как маркетинговый лендинг. Чёткая иерархия блоков, спокойная нейтральная палитра с одним акцентным цветом для важных отметок, моноширинный шрифт для технических деталей (статусы, даты), более человечный шрифт для заголовков. Цель верстки — «пробежать глазами за 30 секунд», а не «внимательно прочитать».

Чек-лист перед встречей (базовый набор):
- [ ] Название и сфера деятельности подтверждены официальным реестром
- [ ] Известны ФИО и должность ЛПР
- [ ] Дата образования компании и налоговый статус проверены
- [ ] Нет неучтённых стоп-факторов (долги, суды)
- [ ] Есть 1-2 факта для small talk
- [ ] Карточка перечитана за 5 минут до встречи

## 9. Ограничения и известные риски

- **Данные о фактически уплаченных налогах (суммах) публично почти нигде не раскрываются.** В Казахстане kgd.gov.kz даёт только бинарный статус «есть/нет задолженность» и налоговый режим, но не суммы. В России nalog.ru («Прозрачный бизнес») даёт больше — вплоть до финансовой отчётности. Продукт должен честно показывать статус, а не выдавать точные суммы там, где их нет.
- **Данные о «где обслуживается клиент»** (банк, подрядчики) редко доступны напрямую и часто требуют косвенных сигналов (тендеры, пресс-релизы) — точность этого блока изначально ниже остальных.
- **Персональные данные ЛПР** — юридический риск при хранении/публикации; требуется явный дисклеймер и ограничение на использование только публичных источников.
- **Актуальность данных** — реестровые данные могут устаревать; нужно показывать дату последнего обновления карточки.

## 10. Метрики успеха

- Время подготовки к встрече сокращается с ~30-40 минут ручного поиска до ≤5 минут.
- Доля полей карточки, заполненных данными (а не «не найдено»), — целевой ориентир ≥70% для блоков «Компания» и «ЛПР».
- Субъективная оценка пользователей: карточка помогла чувствовать себя увереннее на встрече (опрос после пилота).

## 11. Объём MVP (для учебной сессии)

**Входит в MVP:** форма ввода → веб-поиск по 4-6 целевым запросам → LLM-суммаризация по 5 блокам → карточка на экран → базовый чек-лист.

**Не входит в MVP:** история карточек, экспорт в PDF, автообновление, интеграция с платными API (Kompra, Kontur.Focus и т.п.) — эти источники можно подключить на следующей итерации, если потребуется точность выше, чем даёт открытый поиск.

## 12. Открытые вопросы

- Нужна ли интеграция с платным агрегатором (Kompra.kz / Kontur.Focus) для повышения точности блока «Налоги» и «Компания», или открытого поиска достаточно для целей продукта?
- Как часто нужно обновлять карточку для одного и того же клиента (разово перед первой встречей или перед каждой)?
- Нужно ли хранить карточки после встречи или удалять сразу же после использования?
